## 時間について

1イベントあたりの時間は、だいたい次の式になります。

> （2 × 窓の数 × 1 run の時間）÷ 同時実行数

| 規模 | PE の run 数 | 10並列での時間 |
|---|---|---|
| 100イベント × 100窓 | 20,000 | 約 2000 時間（**約3か月**） |
| 100イベント × 40窓 | 8,000 | 約 800 時間（約1か月） |
| **30イベント × 40窓** | 2,400 | 約 240 時間（**約10日**） |
| 30イベント × 20窓 | 1,200 | 約 120 時間（約5日） |

これとは別に、背景テストが1イベントあたり数十分〜1時間ほどかかります。こちらは何イベントでも並列で回せます。

**おすすめは「イベントを多く、窓は少なめ」です。** 見たいのは「イベントをまたいだ fp と PE の関係」です。そのため、1イベントの比を精密に測るより、点（イベント）の数を増やすほうが効きます。窓40本でも、1イベントの比の誤差は ±25% 程度です。30点あれば、回帰の傾きは十分に決まります。

ちなみに、O3（GWTC-2.1 と GWTC-3）の confident なイベントは、L1 のデータがあるものだけで約 90 個のはずです。「100イベント」は、O3 をほぼ全部使う規模です。

**速くする手段**

- **nlive を下げる：** 500 → 250 で、だいたい2倍速くなります。
- **計算機を足す：** 学校の PC と自宅の PC で、イベントを分けて回します。
- **likelihood を速くする：** bilby の relative binning を使えば、1桁くらい速くなる可能性があります。導入の手間はかかります。
- **本格的な大規模化には DINGO：** 本気で 100イベントやるなら、DINGO が本命です。「Bilby で30イベント、DINGO で拡張」は、博士課程への筋としてもきれいです。

## 自動化の一式

GWOSC はこちらの環境から接続できなかったので、5つのファイルとも**文法チェックまでで、実行は未確認**です。まず `--max 3` で試してください。

| ファイル | 役割 |
|---|---|
| `make_event_list.py` | GWOSC の API（`gwosc` パッケージ）から、O3 の confident イベントの名前と合体時刻を取得します。L1 の 4096 s / 4 kHz の HDF5 をダウンロードして、`events.csv` を作ります |
| `bg_auto.py` | `events.csv` の1イベントについて、局所 PSD 版の背景テスト（real と sim）を回します。過渡ノイズ窓とエピソード窓の時刻を `{名前}_L1_bg_windows.json` に保存します |
| `pe_campaign.py` | `events.csv` からイベントを自動で読みます。上の json の窓を PE 窓から除外するので、**背景と PE で「静かな窓」が揃います**（前回の方針 a） |
| `collect_campaign.py` | 背景の CSV を、命名規則から自動で探します。イベントが12個を超えたら、図のラベルを省略します |
| `run_all.sh` | 上の4つを順番に、並列で全部回します。PE の結果がもうある窓は飛ばすので、途中で止めても再開できます |

**使い方**

```bash
python make_event_list.py --max 3        # まず3イベントで試す
cut -d, -f1 events.csv | tail -n +2 | xargs -P 3 -I{} python bg_auto.py --event {}
python pe_campaign.py --event <名前> --list   # 除外窓が出ているか確認
bash run_all.sh 40 10                    # 本番: 1イベント40窓、10並列
```

**注意点**

- **イベント名の形式：** 新しい方式では、イベント名がフル名（例：`GW200129_065458`）になります。今ある3イベントの結果（キーが `GW200129` などの短い名前）とは、別のイベントとして扱われます。今の結果は残しておいて、新しい結果は `--outroot campaign_v2` のような別の場所に出すのが安全です。
- **SNR の偏り：** 事前分布は全イベントで同じ `injection.prior` を使います。そのため、感度の悪いイベントでは SNR が低めに偏ります（GW200129 で起きたこと）。`events.csv` に `prior` 列を足せば、イベントごとに別の prior ファイルを使えるようにしてあります。
- **`bg_auto.py` の依存：** 既存の `bgtest_func.py` と `bgtest_func_frac.py`（`generate_PSD_gauss` と `calibrate_thinning_band`）を import しています。同じフォルダに置いてください。
- **データの欠け：** NaN を含むデータでは、合体時刻を含む連続区間（なければ一番長い区間）だけを使います。窓が少なくなるイベントも出ると思います。
